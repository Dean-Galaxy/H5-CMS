## 独立进程并发：诊断与边界

00 旧日志中子进程 exit=null、输出为空、10 秒内未出现 ready，只能证明未在窗口内报告就绪。02 本地未复现该外置盘启动停滞，不能认定磁盘是根因，也不能把这次本地通过写成 00 外置盘已通过。

旧测试有两个可确认的诊断缺口：20 秒进程超时把启动和执行业务混在一起；握手断言提前失败会释放父锁，却未保证终止子进程。修复后的测试：

- 子进程在加载依赖前即输出 entered，随后逐阶段输出 autoloaded、bootstrapped、guarded、ready、result/error；失败记录 stderr、退出码和最后阶段，核对 Content 实际加载自当前工作区。
- 启动预算 60 秒、真实争锁预算 10 秒、解锁后的执行预算 20 秒分别计算。延长启动预算只是允许较慢环境启动，不等于诊断出了 00 原因。
- 父进程先持有 Content 设置行锁；两个独立 PostgreSQL PID 都进入 `wait_event_type=Lock` 且有实际 blocker 后才解锁。未观察到真实争锁即失败，不能仅凭 ready 判定通过。
- 失败时先终止并回收所有子进程，再释放父锁，保留诊断 JSON；业务断言保留重复发生时间防重和定时与手动发布、改计划、下架并发。
- 额外用例人为延迟启动 12 秒，之后仍真实争锁和防重；另外注入 0.4 秒启动超时及明确启动异常，检查错误阶段、子进程全部结束、父事务关闭、无发布副作用。

[concurrency.json](concurrency.json) 包含 7 次运行。4 次正常启动耗时约 0.20–0.23 秒，解锁后约 0.025–0.036 秒；12 秒故障注入用例启动约 12.26 秒、执行约 0.059 秒。两次标为 failed 的记录是刻意注入、已被测试正确断言的失败，不是套件未通过。具体计时以 JSON 为准。
