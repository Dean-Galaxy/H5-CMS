## 真实问题输入与本地根因

00 报告 C 原300美分已真实部分退款100，官方 Refund completed、Sale partially_refunded；本地退款/付款已记100，区间/权益保留，官方 SUSPENDED、renewal=false、desired=false、refund_stopped=true，但 resolution=true，两个 cancel succeeded、没有 pending，退款 Inbox 仅一条 processed/attempts1。以上是 **00 的现场复核输入**，03 未自行重新访问真实资源；不把这份输入当作修复后已验证。

两个顺序均可独立复现，**不需要并发或重复的同一事件**：

1. 退款通知先处理：`refund` → `syncRefunds` 写停止意图/待核 → cancel 成功 → `sync` 完整核对清为false；随后 `billing:reconcile` 先 `sync(subscription)`，再 `syncRefunds(payment)`。旧后者只要 Sale 非completed就无条件写 resolution=true，结尾 retryPending 只补偿 renewal=true，已停止单因此一直待核。
2. Sale 轮询先发现部分退款：先持久停止意图并确认 SUSPENDED，随后实际 Refund ID 的通知到达。旧 `syncRefunds` 又写true；`refund` 再调用取消，`cancelAccount` 因resolution=true越过“已停止”快返，创建第二条操作。`cancelOperation` 只需读回已 SUSPENDED 就标成功，所以会有两个 succeeded、却未必有第二次 suspend POST。

使用**旧 a7b5454 源码 + 新回归**实际得到2项失败/90断言：第一个次序为完整循环后true≠false；第二个次序为取消计数2≠1。[旧版本红证据](../evidence/03/paypal-refund-resolution-20261029/baseline-reproduction.txt)。测试只在03自己的 `_test` 数据库运行，旧源码实验后立即恢复修复版再运行绿测，没有变动真实环境。

## 最小实现

- `syncRefunds` 持账号锁后重读当前订阅，避免使用 HTTP 读取前的旧本地停止状态。原 desired_renewal **严格false**、renewal_enabled **严格false**、provider_status 为 SUSPENDED/CANCELLED/EXPIRED 时，视为已有停止确认。
- 相同已确认停止下仍保存退款事实和停止意图，但**不再无条件设置 resolution=true，也不写 resolution=false**。其他待核原因原样保留；金额、周期、付款时刻或网络读取错误只能由完整订阅核对处理。未确认停止、状态未知、标志矛盾或没有原停止意图时仍置待核。
- `refund` 在已确认停止且没有 pending 操作时不再发起另一取消；即使存在其他财务待核，也不靠重复取消尝试“修好”它。有原 pending 操作时继续复用原操作，由官方读回确认后完成，不制造新操作或重复 suspend。
- 不改 Refund/Sale 的归属、金额/币种、周期证据、累计退款、权益区间和首惠逻辑；不改变 Stripe、API off、回调验签或生命周期规则。没有新增官方接口请求。
