## 问题与修正

旧X的一般重试分支等目标account_link进入unconfirmed/conflict后，就取全部purpose的PATCH计数，截图并等400ms断言计数不变。前端complete此时还可能正在正常提交advertising。若其csrf/身份读取稍慢，合法的advertising首次PATCH会在取快照之后到达，触发“No automatic replay”，即使account_link没有自动重发。

这是源码审查和纯内存异步反例确认的观察器风险，尚未实际重现，不是产品缺陷，也没有lost-purpose-json/en实际失败记录。不能通过扩大400ms、删除断言或补跑用户来掩盖。

本次仅在一般else分支保留status-429初始按钮isDisabled断言之后、全量PATCH快照之前，等待另一项advertising达到saved。`settleInitialAdvertising`只在目标account_link且非identity-unavailable时执行该等待；独立完成/停止分支另有显式跳过保护，便于纯内存测试。等待失败会直接拒绝，不能先取快照或进入后续观察。

| 分支 | 处理 |
|---|---|
| lost-purpose-json、network-before-purpose、status-419/422/429、actual-cas | 初始目标状态及429初始disabled核验后，先等advertising=saved，再取原全量计数 |
| partial-503 | 原目标advertising；原先等待account_link=saved保持，不增加advertising等待 |
| identity-unavailable | 初始两项无法保存；不等advertising，原身份恢复及后续两项显式保存不变 |
| status-401/403 | 原停止分支保持，不进入一般重试或该等待 |
| lost-registration-json | 原独立完成分支保持，不进入该等待 |

400ms全量计数断言原样保留。另项首次保存完成后若再出现额外PATCH，仍然失败。单项重试/operation及expected_revision、CAS竞争与重试、429 fixture/真实429 guard、首跳禁重定向/重试、锁、pacing、截图/数据来源与业务期望均不改。
