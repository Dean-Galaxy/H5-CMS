## 周期结论与官方依据

截至本次查询，现行 REST Subscriptions v1 的公开接口目录和官方测试页中，**未找到适用的 Test Clock、推进时间或立即触发正常下一周期扣款工具**。这是所查公开材料的结论，不宣称排除了 PayPal 未公开的能力。旧 Classic/Braintree、Webhook 模拟器、改本机时间均不能替代真实自动扣款。[接口目录](https://developer.paypal.com/api/subscriptions/v1)、[官方测试流程](https://developer.paypal.com/platforms/subscriptions/test-subscriptions/)

周期枚举为 DAY/WEEK/MONTH/YEAR，interval_count 最小 1，因此最短可配置 DAY/1。本站保持 WEEK/1；等待 B 实际返回的 `next_billing_time` 和真实新交易，不承诺 Sandbox 首期恰好是付款后 168 小时，不用订单创建时间推算。[Billing Cycle 定义](https://developer.paypal.com/api/subscriptions/v1/definitions/billing_cycle/)

`POST /v1/billing/subscriptions/{id}/capture` 的 capture_type 是 `OUTSTANDING_BALANCE`，金额不能超过欠款。它是追收欠款，不是“立即正常续扣”；不可对 B 用它冒充续费。[Capture 定义](https://developer.paypal.com/api/subscriptions/v1/subscriptions-capture/)

官方测试页的 ERRSUB 参数用于模拟 API 错误响应。它可补接口错误处理证据，不会证明真实资金失败、真实下一周期或失败补款。不要为这些测试值放宽现有生产对象 ID 校验；若 00 排协议探针，放在隔离工具且不接账本。[官方 negative testing](https://developer.paypal.com/platforms/subscriptions/test-subscriptions/)

## 00/06 运行边界及 B 的对账

00 已确认：**今日窗口结束即关闭 API、新购、本机进程和公网，不跨 A 到期无人值守运行**。关闭本站 API/站点不等于取消 B 在 PayPal 的自动付款授权；B 保持官方 ACTIVE 才能等待自动续扣。需在首款确认前向本人说明仍会使用 Sandbox 测试资金续扣；不会收费到 Live。关闭回调期间通知可能延迟/重试，恢复时由 00 核对并补偿，不能将暂停网站误报为暂停订阅。

当前 `PayPalReconciliation::sync` 默认允许生命周期动作：SUSPENDED 且 desired_renewal=false，在已付期结束后可调用官方 cancel。`billing:reconcile` 及 `process` 通知路径均会使用默认 sync。因此：

1. A 到期消费验收保持 API off，只读 MembershipReader；不跑开启 API 的全局对账来“只读核对”。
2. B 后续由 00 从私密记录核准本人/订单/provider scope/订阅 ID，再定向 `sync(B, allowLifecycleChanges: false)`。它只禁止 sync 自身的过期审批/暂停转终止分支，**并非所有内部退款处理绝无远端动作**；先查 B 无退款/停止意图。
3. 无现成按对象筛选的 worker CLI 可直接承诺隔离：处理通知前核事件归属，不能直接 drain 全队列。`process` 遇 SALE 会读真实 Sale 再查本地订阅，SUBSCRIPTION 事件直接按对象查订阅，随后默认 sync；A 的历史通知不在本批处理。需要工具时由 00 单对象控制，不改正式全局行为。
4. B 每次核对记录读取前后支付计数、已有周期不变、新周期边界/原价、事件类型和处理状态。若历史不全、签名/归属/金额/状态不一致，保留待核，不补造付款或按现在加七天。付款事实与 outbox 按现事务落地，广告端失败不回滚付款。
5. B 真正续扣验收结束后，由本人按“会员 → 取消未来续费”操作，00 重读官方停止状态。停止失败继续处理中；不自动退款、不提前撤销当期。

## D 恢复专用实验：先证明协议，再开放 F01

由 00 另排 D（不能是 A 或等待续扣的 B）：

1. 本人完成 D 专用 WEEK/1 付款，记录首款和原下一次时间；离下次边界足够远、无欠款/失败/退款/待核、原 Plan 未调价，方可暂停并读回 SUSPENDED。缺下一次时间即不继续。
2. 本人主动确认恢复对象、原约定常规价和原下一次时间。00 保存私密操作意图与基线：Plan/订阅/执行次数、交易列表、Sale 集合及权益原区间；只对该 ID 单次 activate，不 PATCH start_time、不 revise、不 capture、不新建第二份。
3. 响应未知先 GET 重读，不盲目重复 activate。恢复后重读 ACTIVE、原 Plan/价格及 next_billing_time 与基线一致；即时及短观察窗口再次读完整交易，不能多一笔。记录观察时长，不把短窗口无新增交易写成永久保证。
4. 最终强证据还需等到**原定**下次时间，证实该时间之前无新增扣款、该周期只有一次原价续扣。提前扣款/时间变化/证据不足均不通过；按批准收尾停止 D，不调整账本掩盖差异。
5. 此协议实验不代表现有站内按钮可用。00 接收语义后，03 才将 PayPal 接入既有 F01：本人原订阅报价、5 分钟及原期边界有效期、确认版本、同凭证防重、旧重试不能撤销后来取消；另做站内全链路验收。当前不可用状态保持。

## C 退款专用实验：不新建普通退款审批流

当前 Subscriptions 交易定义区分 PARTIALLY_REFUNDED/REFUNDED，订阅通知仍使用 PAYMENT.SALE.REFUNDED。[交易定义](https://developer.paypal.com/api/subscriptions/v1/definitions/transaction/)、[通知清单](https://developer.paypal.com/subscriptions/webhooks/)

建议本轮由本人在 **Sandbox 商户交易页面**核准 C 对应原 Sale 后操作，03 仅同步真实结果。若 C 原款确为 300 美分，可先退 100、核实成功后再退剩余 200；金额以 00 实际锁定的 C 为准，不从用户浏览器入参相信金额。每步均需 Refund ID→Sale→原订阅/订单、USD 金额及实际成功状态，部分阶段确认保留权益并停止续费，累计全额只撤销该付款权益。未出现 completed、官方结果未知或 pending 时不继续下一步、不先撤权；失败退款与真实成功分开。

检索 Sale refund API 时，官方现在将 `/v1/payments` 文档标为 **Deprecated**，因此不将该页当成新 REST Subscriptions 的新能力，也不擅自新增退款写接口；更不能把 Sale ID 当 v2 capture ID。现有读取 Sale/Refund 的兼容性仍须本批真实结果验证，若页面/对象映射不符即保留缺项交 00，不凭旧样例强行接通。[官方旧 Sale refund 标记](https://developer.paypal.com/api/deprecated/payments/v1/sale-refund)

## 失败与补款的未完成项

官方失败说明为每隔 5 天重试、每周期最多两次，并受失败阈值影响；示例 auto_bill_outstanding=true/threshold=2 与本站 false/1 不同，不能照搬其合并扣款结果。[失败与余额恢复](https://developer.paypal.com/platforms/subscriptions/customize/payment-failure-retry/)

未找到上述现行材料提供可强制真实续扣失败的专用开关；不承诺“清空买家余额”必定失败（可能有其他资金来源）。真实失败方案须由 00 核准官方可复现的方法/专用资金设置后另测。现有 `WeeklyCycleEvidence` 对 last_failed_payment、欠款、失败数或不连续/合并周期拒绝推断；这是安全待核边界，**不是已实现真实失败补款映射**。未来必须用官方实际交易与周期归属补齐工程，并交 00 冻结需要的公共变化。
