## F05：首周优惠请求带入互斥 Checkout 参数

**责任：03；优先级 P1，接收前修复。**

触发：新用户购买低于常规周价的首周套餐。例如常规 1200 美分、首周 300 美分（均为隔离测试样例）。`StripeGateway::prepareCheckout` 同时放入 `allow_promotion_codes=false` 和 `discounts[0][coupon]`；锁定 Stripe PHP 客户端实际序列化后，前者仍作为字符串 `"false"` 出现在 HTTP 参数中，没有被删除。

- 首个不一致环节：`h5-platform/app/Modules/Billing/Gateway/StripeGateway.php:169` 以及添加 coupon 的 175—184 行；`preparedRequest` 的约束也要求这个字段为 false，因此不能只删创建参数而不调整校验。
- 原测试缺口：`h5-platform/tests/Feature/Billing/StripeGatewayTest.php:206` 反而断言带有该 false 参数；HTTP 桩无条件返回成功，没有覆盖平台参数互斥。
- 已观察的本机事实：[参数截获](../evidence/00/billing-reception/checkout-parameters.json) 同时显示 coupon 已附加、促销码字段存在且序列化为 false；[新增检查](../evidence/00/billing-reception/reception-probes.txt) 中对应断言失败。
- 外部兼容性依据：[Stripe 官方仓库原始问题 1076](https://github.com/stripe/stripe-node/issues/1076) 记录这两个参数即使一项为 false/null 仍有互斥拒绝；[Cashier 原始问题 1163](https://github.com/laravel/cashier-stripe/issues/1163) 专门复现了 false 情况。当前锁定 Cashier 的 CheckoutBuilder 也用 array_filter 去掉 false。较新的 [Stripe 仓库问题 2248](https://github.com/stripe/stripe-node/issues/2248) 仍记录两参数互斥。
- 证据限度：这些是历史平台兼容性记录，加上本次真实 SDK 参数截获；**没有使用公司账号实测本候选的 Stripe 拒绝响应**。不能把本地桩写成官方结果。当前请求重现已知不兼容写法，应先去掉无须发送的促销码参数，再补官方测试。

用户层面的影响：首周优惠可能打不开付款页；若平台拒绝，现有保守处理会保留“付款处理中”的占位。这不是缺公司账号就能解释的空项，也不需要用户重定价格或优惠规则。
