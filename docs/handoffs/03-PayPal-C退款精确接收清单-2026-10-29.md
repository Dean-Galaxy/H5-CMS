## 官方界面、账号和权限：已查文档，实际页面待验

官方 US Help101 目前仍提供 Activity → 选中付款 → Issue a refund → 输入金额 → Continue → 审阅后 Issue Refund，支持付款后 180 天内全额或部分退款，提交后不可取消。[官方退款操作说明](https://www.paypal.com/us/cshelp/article/how-do-i-issue-a-refund-help101)

官方订阅测试页要求用 Developer Dashboard 内 **Sandbox Business** 账号登录 `www.sandbox.paypal.com/billing/subscriptions` 核商户收到的订阅；买家 Personal 账号是另一角色。[官方订阅测试流程](https://developer.paypal.com/platforms/subscriptions/test-subscriptions/)

本方案将上述通用退款导航作为 Sandbox 商户页面的**候选操作路径**；这是结合两份官方说明的推导，不是已观察到当前 Sandbox 账号的按钮。先由本人/00 实际登录同一 Sandbox Business，核账号归属、C 交易详情、退款入口和最大可退余额。Developer 应用页、站内后台、买家 Activity 均不能替代该商户交易操作。

主商户账号和次级用户权限不同。官方提供 Account Settings → Manage users → View profile → Permissions 管理次级用户权限；本方案没有查到足以保证当前 Sandbox 次级用户必有退款权的材料，不臆造具体权限名称。若实际页面要求另一个授权/审批，先完成对应人工权限核准，不绕过、不擅自扩权，也不把“已提交审批”写成已退款。[官方 Business 用户权限说明](https://www.paypal.com/us/cshelp/article/how-do-i-manage-users-on-my-business-account-help274)

旧 `/v1/payments` API 文档的 Deprecated 标记只描述该 API 文档/接口状态，**不能据此推定商户界面不能退款**。本批不添加退款写 API，也不将 Sale ID 当作 v2 Capture ID。现有官方读接口在当前 App 对真实 C Refund 是否有权限，仍须实际 GET 核准。

## 当前实际代码路径和字段

| 环节 | 实际代码及可信字段 | 接收时必须检查 |
|---|---|---|
| 接收 | `PayPalWebhookReceiver` 原正文/五头 → 固定官方验签 → `ProviderInboxStore` | 签名成功并可靠收件才 HTTP 200；scope/event ID 独立。同事件 200/重复不增加付款事实 |
| 退款提示 | `SandboxWebhookEnvelope` 将 `PAYMENT.SALE.REFUNDED` 分类为 refund_lookup，取 resource.id；`PayPalReconciliation::process` 调 refund(scope, object_id) | 目前假设 resource.id 为 Refund ID；须用真实事件及官方读回核实，不能拿通知自带金额直接记账。若真实形状不同，停止并交 03 定向修复 |
| Refund 读回 | `SandboxApi::refund` GET `/v1/payments/refund/{id}` | `id` 精确相同；`sale_id` 为已锁定 C Sale；`amount.total` 由 USD 整数转换，第一笔 100、第二笔 200；`amount.currency=USD`；state 只接受 pending/completed/failed/cancelled，completed 才映射 succeeded |
| 原 Sale 读回 | `SandboxApi::sale` GET `/v1/payments/sale/{id}` | `id` 为 C 原 Sale；`billing_agreement_id` 为 C 官方订阅；原款 `amount.total=3.00`/currency=USD；state 仅 completed/partially_refunded/refunded，否则待核，不按成功处理 |
| 退款累计 | `syncRefunds(C payment)` 重新 GET 已登记各 Refund，核 ID/Sale/原金额不变，再核 Sale | 已成功退款的金额相加 ≤300；部分阶段已知累计100；全部退款 Sale state=refunded 可独立证明原300全额已退，即使第二条退款通知漏达也不捏造第二个 Refund ID |
| 权益/订单 | 同事务更新该 payment.refunded_amount_minor、仅 payment_id 匹配的 entitlements.revoked_at、该 order.payment_state | 部分100保留原区间；累计全额300撤对应区间；access_from/until 不改，不从现在加时；其他付款区间不改，首惠消费记录保留 |
| 停止续费 | 非 completed 的 Sale 状态写 refund_stopped=true、desired_renewal=false、resolution_required=true；`refund` 随后调用 `cancelSubscriptionForRefund` | **停止意图不是停止成功**。ACTIVE 通常调用 suspend，并重读官方 SUSPENDED/终态；未知/失败维持 pending，不能向本人报成功 |

官方当前订阅通知表仍列 `PAYMENT.SALE.REFUNDED`。[订阅通知清单](https://developer.paypal.com/subscriptions/webhooks/)。读取字段依据官方 [Refund 详情](https://developer.paypal.com/api/deprecated/payments/v1/refund-get) 和 [Sale 详情](https://developer.paypal.com/api/deprecated/payments/v1/sale-get)；两页目前均标 Deprecated，本批真实兼容性要实际验，不以文档样例代替真实结果。

## 分步操作与通过门槛

### C0：锁定与备份，尚不退款

00 在私密记录锁定 C viewer/order/subscription/payment/Sale，核 300/USD/已付区间和原价1200；记录原付款、权益、outbox 各一份且首惠已用。记录当前 C 无欠款/失败/停止意图/待办，当前 API/App/scope 未变化。本人或已登录的 00 打开 C 商户交易详情，只读核对原交易金额及 ID；00 明确确认“这笔就是 C，可退额度300”。以实际 C 为准，不能靠“最近一笔”“同样3美元”或买家昵称猜测。

### C1：仅退款 100 美分

1. 本人在 C 交易选择 Issue a refund，输入 USD **1.00**；审阅对象及金额后提交。保存实际退款回执引用/Refund ID；若界面结果未知，先核原交易及退款历史，不再次点击。
2. 00 先只读官方 Refund，核该 ID 的 sale_id 就是私密锁定 C Sale、金额100/USD。此门槛在调用同步入口**之前**完成；`refund(scope,id)` 本身可以处理该商户范围内的任何已知付款，不能靠 scope 自动限制只处理 C。
3. 正常通知应官方验签后入 Inbox，再由核准的单对象路径处理。若无通知，从真实回执获得 Refund ID 后由 00 定向 `refund(C scope, actual Refund ID)`；没有 Refund ID 时不能从 Sale partially_refunded 推出“已退100”。
4. 必须读到 Refund completed、Sale partially_refunded；本地退款 succeeded/100、payment.refunded_amount_minor=100、order.payment_state=partially_refunded、对应 entitlement.revoked_at=null、原区间完全保留、当前会员有效、首惠仍已用。
5. 远端停止必须另核：C SUSPENDED/允许的终态、renewal_enabled=false、desired_renewal=false、refund_stopped=true、resolution_required=false、取消操作 succeeded（如已生成）。不以 refund 方法正常返回、Inbox processed 或停止意图代替这些值。
6. 重读 A/B 原区间与续费状态保持，付款/权益/outbox 不新增。C1 全部通过后才提示本人退剩余200。

### C2：仅退款剩余 200 美分

1. 回到**同一 C 原交易**，核已退1美元、剩余可退2美元；本人输入 USD **2.00**，审阅后提交，保存第二个真实 Refund ID。
2. 00 分别读回两个 Refund，锁相同 C Sale、各100/200/USD/completed；原 Sale refunded、原款仍300，累计300不超退。
3. 处理第二条实际通知或用第二个实际 Refund ID 定向补偿；核 refunds 两条 succeeded 总300，payment.refunded_amount_minor=300，order.payment_state=refunded；仅该 payment entitlement 撤销，原区间字段保持，首惠不恢复，未来续费仍停。
4. 如果 C 只有这一份付款，当前会员应无效；若另有真实有效付款，保留其对应区间并按区间读会员。当前 C 单周期验收不能声称已在真实平台验过“保留另一付费周期”；该分支目前仅有本地两周期回归。
5. 不回滚原付款或删除 outbox，不制造“再付款/再授予”来抵消退款。C 全额退款不自动意味着可立刻重购，唯一占位/待核/原订阅终态另验。

## 当前缺口、失败与补偿

| 情况 | 当前实现/安全处理 | 是否需先修代码 |
|---|---|---|
| 商户页面无按钮/权限/可退额度 | 本人/00 实际 UI 核准；保持已付单，不能改退 A/B | UI 能力待验；不阻止 C 首款，阻止退款动作 |
| 漏部分退款通知且无 Refund ID | syncRefunds 只枚举**本地已知** Refund，并不发现官方新退款；Sale 部分退款可落停止意图，但未知部分金额仍可能是0 | 当前能力缺口；本批可用真实回执 ID 定向补偿。拿不到 ID 就不宣称100已入账，不添加猜测 |
| 直接只调 syncRefunds | 它只保存退款/停止意图，不自行执行远端停止；之后须对 C 定向 `cancelSubscriptionForRefund(C sub)`，再核实际状态 | 操作清单可覆盖，无须先改实现 |
| suspend 500/未知 | 退款事实保留，权益保留，renewal 可能仍 true，resolution=true，取消操作 pending。refund 正常返回/Inbox processed 仍可能发生 | 已有可靠待办；只对 C 的 pending operation ID 调 executeOperation，再读官方结果，不跑全局重试 |

| 第二通知漏达但 Sale refunded | 已知整笔原款可确认300全退并撤对应权益，允许只有第一条本地 Refund 记录 | 可以证明全额撤权；不能声称两个实际退款编号均同步。仍补第二真实 ID 才完成本批“两笔累计”验收 |
| GET权限/状态/币种/原Sale/订阅关系不符 | 拒绝事实或待核，不通过改币种/关联ID/金额/库记录修补 | 真实缺项由00脱敏交03；当前不扩大兼容或增退款写接口 |
| 真通知 resource.id 不是当前预期形状 | 先保留实际官方事件及只读对象关系，HTTP收件/签名与业务处理结果分开；不拿 Sale ID 试充 Refund ID | 若发生才定向修复并复验；当前不能靠 Mock 断言官方形状通过 |
