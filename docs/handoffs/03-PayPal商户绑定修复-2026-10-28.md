## 当前机制和证明边界

- 初始化采用 **operator_dashboard** 来源：本人/07在官方后台核对同一Sandbox Merchant App关联的Business账号，再核对该账号Merchant ID，并核对本机已保存的Client ID确属该App。00/07保留私密依据，给出非个人资料回执号。**不能仅凭手填ID或OAuth200生成三个确认true。**
- 模块持久绑定 `sandbox + merchant_scope + Client ID SHA256 + Merchant ID`，记录来源、核对时间、回执引用及文件hash。此绑定属于有来源的人工核对，不是PayPal API自动识别商户。OAuth成功只证明App凭据有效，忽略OAuth app_id。
- 同scope不可覆盖绑定，同Client ID指纹不能悄悄转另scope；Client ID、Merchant ID、scope变化均拒绝沿用，须另行审查旧账务迁移。Secret轮换不改变App绑定，但须用新Secret通过官方认证；不留旧token绕过失败。
- 运行继续逐项核对产品→原计划→订阅→站内订单/custom_id与scope→Sale金额/币种/周期。Catalog/计划访问可能是商户账户级权限，**不宣称App独占**。
- 新购和通知收件前，用当前App凭据读取 `/v1/notifications/webhooks/{id}`，比对实际ID、精确预期HTTPS URL和必需事件覆盖。配置URL只作比较，程序不请求该URL。
- 缺绑定、绑定不符或Webhook核对失败，购买和收件返回 `DEPENDENCY_NOT_READY` 503；不创建支付订单、不确认收件、不授予权益。取消/退款/对账仍要求原绑定及官方对象事实。
- 余额请求和 `merchantIdentity()` 已移除，没有引入非订阅Orders探测、激活/立即扣款、真实退款创建或自动启用新购。原Stripe继续保留，PayPal恢复续费仍关闭。

### 私密回执字段

| 字段 | 要求 |
|---|---|
| binding_source | 固定operator_dashboard |
| environment | 固定sandbox |
| merchant_scope | 与当前固定商户别名相等 |
| merchant_id | 官方关联账号实际核对结果，须与本机配置相等 |
| client_id_sha256 | 本机同一Client ID的SHA256，与离线context相等 |

## Webhook事件范围与官方依据

必需覆盖：`PAYMENT.SALE.COMPLETED`、`PAYMENT.SALE.REFUNDED`、`PAYMENT.SALE.REVERSED`，以及 `BILLING.SUBSCRIPTION.CREATED`、`ACTIVATED`、`UPDATED`、`SUSPENDED`、`CANCELLED`、`EXPIRED`、`PAYMENT.FAILED`（后七项均带同一BILLING.SUBSCRIPTION前缀）。07建议明确选这十项以缩小范围。官方读回精确`*`也可满足覆盖，因为官方文档明确它代表当前和未来所有事件；空/坏列表或缺项且无`*`拒绝。

依据：[官方App与Business关联说明](https://www.paypal.com/us/cshelp/article/how-do-i-create-paypal-rest-api-credentials-ts1949)、[OAuth与App认证边界](https://developer.paypal.com/api/rest/)、[Webhook GET](https://developer.paypal.com/api/webhooks/v1/webhooks-get)、[Webhook事件与通配定义](https://developer.paypal.com/api/webhooks/v1/webhooks-post)。这些支持接口含义；人工初始化绑定是本项目经00接收的设计，不是PayPal提供了新的自动身份接口。
